# Бриф для агента бэкенда (параллельно с волной 1 дизайна, UX1.1)

Составлен 2026-09-24. Прочитай целиком до первого действия.

## Что происходит в репозитории прямо сейчас

- В рабочем дереве `plane-fork` **без коммитов** лежат две волны редизайна фронтенда:
  - волна 0 (UX0.2) — готова;
  - волна 1 (UX1.1) — идёт, агенты правят `apps/web/**` и `packages/**` примерно до 12:00 25 сентября.
- Dev-сервер фронтенда на `:3000` запущен владельцем. API работает в docker на `:8000`.

## Правила, чтобы не сломать друг другу работу

1. **Файлы.** Правь только бэкенд: `apps/api/**` (включая миграции и тесты) и документы своей карточки.
   В `apps/web/**` и `packages/**` не заходи до конца волны 1. Если задаче нужен интерфейс, опиши, что нужно,
   в заметке (см. ниже) — фронтенд сделает агент дизайна.
2. **Git.** Никаких `git add -A`, `git add .`, `git stash`, `git reset`, `git checkout -- …`, `git clean`,
   `git rebase`. Если коммитишь, то только свои файлы по явным путям (`git add apps/api/…`). Не коммить чужие
   изменения в `apps/web` и `packages`: там незакоммиченная работа двух волн.
3. **Серверы.** Dev-сервер фронтенда (`:3000`) не перезапускать и второй не запускать. API в docker
   перезапускать можно.
4. **Общие документы.** В `docs/project-spec/…/CHANGELOG.md` и `tasks/README.md` только добавляй строки,
   ничего не переписывай.

## Какие задачи дадут больше всего пользы прямо сейчас (рекомендация дизайна)

Все три — небольшие, аддитивные, без изменения существующих полей. Сейчас волна 1 честно показывает только
вычислимые данные; эти доработки сделают её экраны полнее.

### B1. Состояние PR в связях задачи

- Где: `serialize_link` в `ppm_git` — ссылки задачи на Git-объекты.
- Что добавить (аддитивно): поле `git_object` — `null` для ссылок не на Git, иначе
  `{ "provider": "github", "kind": "pull_request" | "branch" | "commit", "number": 48, "title": "…",
  "state": "open" | "closed" | "merged", "is_draft": false, "url": "…", "updated_at": "ISO-8601" }`.
- Данные уже есть в `PpmGitObject`. Существующие поля ответа не меняются.
- Тест: контрактный — старые поля на месте, новое присутствует и `null` для обычных ссылок.
- Во фронтенде это станет «#48 · открыт / черновик / слит» в колонке «Материалы».

### B2. Лента изменений проекта (только чтение)

- `GET /api/ppm/v1/workspaces/<slug>/projects/<project_id>/work-items/activity/?limit=20&before=<ISO>`
- Ответ: `{ "results": [ { "id", "work_item": { "id", "sequence_id", "name" }, "actor": { "id", "display_name" },
  "field", "verb", "old_value", "new_value", "created_at" } ], "next_before": "ISO | null" }`.
- Источник: `IssueActivity`. Видимость — через `get_visible_work_items` (`ppm_canvas/services.py`), права — участник
  проекта (включая читателя). Никаких e-mail и лишних персональных данных.
- Тесты: права (чужой проект — 403/404), видимость, пагинация, `limit` ≤ 50.
- Во фронтенде это станет «Недавно изменённые» с описанием изменения («статус: В работе → На проверке»).

### B3. Статус «На проверке» в новых проектах

- При создании **нового** проекта PPM добавить статус «На проверке» (группа `started`, между «В работе» и «Готово»).
- Существующие проекты не трогать; миграций данных нет. По желанию — management-команда, которая добавляет
  статус в указанный проект (запускает владелец).
- Тест: новый проект получает статус, старые — нет.
- Во фронтенде заработает секция «Ждёт проверки» в колонке «Требует внимания».

## Как сообщить, что готово

После каждой доработки допиши в `docs/superpowers/plans/2026-09-24-ux11/BACKEND-API-NOTES.md`:
эндпоинт или поле, пример ответа, ссылку на тест и статус (готово / в работе). Агент дизайна читает этот
файл и подключает интерфейс: сразу, если успевает в волне 1, иначе отдельным шагом после неё.
