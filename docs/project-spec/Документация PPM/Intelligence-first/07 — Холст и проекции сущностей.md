# 07 — Холст и проекции сущностей

Текущий web-перенос охватывает ноды и проекции из действующей матрицы 21.
Существующие AI/agent shapes сохраняются для совместимости старых snapshot,
но новые функции для них не входят в план PPM 1.0.

## Назначение

Canvas — пространственная карта контекста проекта и основной интерфейс AntyFlow внутри PPM. Он не заменяет task
tracker, файловое дерево или Git provider: он связывает их объекты, даёт Project Brain управляемый контекст и
предоставляет команде общее визуальное рабочее пространство.

## Project Canvas и доски

- у каждого проекта автоматически создаётся ровно один активный Project Canvas;
- внутри Canvas может быть любое количество активных и архивных досок;
- первая доска называется `Главная`;
- команда открывает несколько досок вкладками и быстро переключается между ними;
- каждая доска имеет собственные snapshot, version sequence, bindings, semantic edges и realtime room;
- доски принадлежат проекту, а не отдельному участнику;
- личными остаются только UI preferences: последняя открытая доска, масштаб и состояние боковых панелей;
- при открытии проекта загружается список досок и активная доска, а не snapshots всех досок сразу.

Каноническое решение и матрица переноса: [Решение — Полноценный AntyFlow Canvas в web PPM](<Решение — Полноценный AntyFlow Canvas в web PPM.md>).

## Что переносится из AntyFlow

### Можно переиспользовать концептуально и частично по коду

- tldraw как основа бесконечного холста;
- единый `flow-node` и versioned `props.extra`;
- заметка/Markdown preview;
- визуальные стрелки;
- node type registry;
- PDF/image preview UI;
- схемы Mermaid;
- визуальные темы AntyFlow;
- извлечение контекста связанных нод.

### Требует web/server адаптации

- сохранение доски;
- совместный доступ;
- загрузка файлов;
- выбор проекта;
- RAG;
- realtime room authorization;
- project memory.

### Не переносится в browser bundle напрямую

- Electron IPC;
- `fs` и прямой путь к пользовательскому диску;
- `better-sqlite3`;
- `BrowserWindow` и `<webview>`;
- локальный terminal/Jupyter kernel;
- автоустановка sidecars;
- локальные API keys из `%APPDATA%`;
- desktop-only sync через общую папку.

Сценарии действующего объёма реализуются через Vault, server API и
project-authorized realtime. Исключённые AI/agent функции не выдаются за
реализованный web-эквивалент.

## Реализованный базовый набор

### `note`

Короткая заметка, принадлежащая Canvas. Поля: title, Markdown body, color, author, timestamps. Для большого документа UI предлагает `Перенести в Vault`.

### `work_item_ref`

Проекция Plane Work Item. Показывает title, identifier, state, priority, assignees, due date. Локально хранит только binding и display cache.

### `page_ref`

Проекция Plane Page. Показывает title, excerpt и updated state. Полное редактирование открывает Page; inline edit включается позже только через Plane API.

### `vault_file_ref`

Проекция Vault file. Для Markdown показывает excerpt, для PDF/image — preview, для других типов — metadata и download/open.

### `group`

Визуальная рамка с названием, цветом и optional description. Не создаёт Plane Module автоматически. Команда `Связать с направлением` создаёт projection/binding к существующему Module.

### Исторические `agent_query` и `agent_answer`

Ранее созданные query/answer shapes читаются и сохраняются без потери данных.
Их создание и развитие не входят в текущий план.

## Целевой каталог AntyFlow

### Canvas-native content

- `note` — короткая Markdown-заметка;
- `document` — большой структурированный текст;
- `checklist` — локальный список, не являющийся базой Work Items;
- `table` — табличный артефакт Canvas/Vault;
- `code` — кодовый фрагмент с языком и безопасным preview;
- `diagram` — Mermaid/структурная схема без исполнения HTML/JS;
- `image` и `reference` — изображение либо ссылка на Vault/attachment;
- `deck` — презентация или её проекция;
- `group`/`frame` — визуальная область и группировка.

### Проекции источников

- `work_item_ref`;
- `work_items_view` — Kanban/backlog/list поверх Plane Work Items без второй базы задач;
- `cycle_ref` и `module_ref`;
- `page_ref`, `attachment_ref`, `vault_file_ref`;
- `repository_ref`, `branch_ref`, `commit_ref`, `pull_request_ref`;
- `external_source_ref`.

### Project Brain

- `search` по разрешённым источникам проекта с проверяемыми citations.

Ноды `diagram`, `image` и `deck` проходят действующие карточки AF.
Ранее созданные AI/job types сохраняются только для чтения старых досок;
новых карточек реализации для них нет.

## Базовый schema ноды

```ts
type PpmCanvasNodeV1 = {
  schema_version: 1
  kind:
    | 'note'
    | 'work_item_ref'
    | 'page_ref'
    | 'vault_file_ref'
    | 'group'
    | 'agent_query'
    | 'agent_answer'
  title?: string
  body?: string
  binding?: {
    entity_type: string
    entity_id: string
    source_version?: string
  }
  visual: {
    color?: string
    collapsed?: boolean
    width?: number
    height?: number
  }
}
```

Изменение `props.extra` требует увеличения `schema_version`, миграции и unit test. Неизвестные поля сохраняются, чтобы downgrade/forward compatibility не уничтожала данные.

## Добавление проекции

```text
Пользователь выбирает Add
→ выбирает тип источника
→ поиск ограничивается текущим project
→ сервер проверяет read permission
→ создаётся shape
→ создаётся binding
→ snapshot сохраняется новой версией
```

Если binding не сохранился, UI не должен оставлять shape в состоянии «как будто всё готово». Он показывает retry либо откатывает локальное добавление.

## Изменение Work Item на холсте

Разрешённый быстрый edit MVP:

- state;
- priority;
- assignee;
- due date.

Перед изменением проверяются capability и `source_version`. Description, comments, dependencies и destructive operations открывают полноценную карточку Work Item.

## Удаление

Контекстное меню разделяет:

- `Убрать с холста` — удаляет shape и binding;
- `Открыть источник` — переходит к canonical entity;
- `Удалить источник` — отдельное опасное действие, показывается только при наличии права и никогда не является default.

## Семантические связи

После рисования стрелки UI предлагает необязательный тип связи. Выбор сохраняет `ppm_semantic_edges`. Направление важно для `depends_on`, `blocks`, `implements`, `evidence_for`, `derived_from` и `result_of`.

Неподтверждённая связь отображается отдельно и не участвует в подтверждённом графе.

## Контекст поиска

При поиске по выбранному контексту scope строится в порядке:

1. явно выделенные ноды;
2. semantic neighbors до заданной глубины;
3. источники bindings;
4. релевантные project sources из индекса;
5. актуальные структурированные поля Plane/Git.

UI показывает пользователю scope: количество нод, документов и источники.

## Сохранение и конфликты

- autosave debounce 800–1500 ms после изменения активной доски;
- request содержит `base_version` и `client_operation_id`;
- `409` не перезаписывает серверный snapshot;
- MVP предлагает reload/copy local changes;
- полноценное merge/CRDT вводится отдельной задачей;
- каждая успешная запись создаёт immutable board version;
- переключение вкладки flush-ит pending save либо явно показывает несохранённое состояние;
- version conflict одной доски не блокирует открытие остальных досок проекта.

## Производительность

- initial Canvas загружает snapshot и bindings одной согласованной операцией;
- heavy previews ленивые;
- поиск источников пагинируется;
- live refresh обновляет display data без записи нового snapshot, если координаты не менялись;
- индексирование не выполняется в browser main thread;
- target MVP: 300 shapes на холсте без деградации базового pan/zoom; отдельный performance gate определяет реальные лимиты.

## Accessibility и UX

- keyboard focus для нод и команд;
- текстовая панель списка объектов как альтернатива canvas-only навигации;
- не полагаться только на цвет;
- tooltip объясняет источник истины;
- статус сохранения всегда видим;
- motion учитывает `prefers-reduced-motion`;
- источники результатов поиска доступны без наведения.

## Acceptance

1. У каждого project ровно один Canvas и минимум одна активная доска.
2. Участник открывает несколько общих досок вкладками; после reload порядок и содержимое сохранены.
3. Work Item, Page и Vault file добавляются только из текущего project.
4. Изменение Work Item видно в Plane-backed разделе «Работа».
5. Удаление shape не удаляет источник.
6. Второй project имеет другой Canvas и другой список досок.
7. Viewer не сохраняет изменения.
8. Удалённый источник отображается как недоступный, а shape не исчезает молча.
9. После reload доска восстанавливает ноды и связи.
10. Ни одна Canvas action не создаёт локальный дубликат Work Item/Page/Vault file.
11. Глобальный администратор открывает Canvas любого проекта; РП/участник получают deny вне membership.
12. Основной UX и каталог функций проходят утверждённую AntyFlow parity matrix.
