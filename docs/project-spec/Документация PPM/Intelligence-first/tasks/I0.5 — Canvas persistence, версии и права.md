# I0.5 — Canvas persistence, версии и права

## Пользовательский результат

Canvas общий для участников одного project, сохраняется после reload/restart, имеет immutable versions и не перезаписывает изменения другого участника молча.

## Зависимости

- I0.4;
- data/API/security документы 05/06/13.

## Scope

- isolated Canvas Django app/models/migrations;
- `ppm_project_canvases`, `ppm_canvas_versions`;
- GET/PUT API;
- project permission adapter;
- optimistic concurrency;
- autosave status UI;
- first-open idempotent creation;
- corrupt snapshot fallback;
- audit metadata;
- two-user/project tests.

## Не входит

- bindings;
- semantic edges;
- realtime/CRDT;
- version restore UI;
- Work Items.

## Порядок реализации

1. Добавить models/constraints и additive migration.
2. Добавить serializers/schema validation/size limit.
3. Реализовать common permission adapter на Plane role.
4. Реализовать idempotent get-or-create active canvas.
5. Реализовать versioned PUT с transaction/lock/precondition.
6. Добавить request/client operation IDs.
7. Подключить Canvas store и debounced autosave.
8. Реализовать `saved/saving/conflict/error` UI.
9. Добавить corrupt snapshot read fallback без silent overwrite.
10. Проверить restart и concurrent clients.

## Критерии приёмки

1. Первый open создаёт ровно один active canvas.
2. Reload/restart восстанавливает snapshot.
3. Project A/B не смешиваются.
4. Viewer/outsider write отклоняется.
5. Stale base version получает 409.
6. Повторный operation ID не создаёт лишнюю version.
7. Corrupt snapshot не роняет project и не перезаписывается автоматически.
8. Каждый successful save имеет author/time/hash.

## Текущее состояние реализации

В Plane fork добавлено изолированное Django-приложение `plane.ppm_canvas` с двумя собственными таблицами: активный Canvas проекта и неизменяемые версии снимков. Plane остаётся источником пользователей, workspace, project и ролей; связь выполняется по UUID без изменения core-таблиц Plane.

`GET /api/ppm/v1/workspaces/:workspaceId/projects/:projectId/canvas/` идемпотентно создаёт один активный Canvas и возвращает current snapshot. `PUT` проверяет Plane membership на сервере, ограничивает snapshot 2 MiB, фиксирует author/time/hash/request ID, создаёт новую version внутри transaction с `select_for_update`, отклоняет stale `base_version` через `409 CANVAS_VERSION_CONFLICT` и безопасно повторяет тот же `client_operation_id` без новой version.

Web Canvas больше не использует browser storage как canonical source. После открытия он загружает server snapshot, сохраняет пользовательские изменения с debounce 1 секунда и показывает состояния `loading/saving/saved/conflict/error/corrupt`. Admin/Member могут редактировать, Guest получает read-only. При конфликте локальное состояние остаётся в редакторе и доступно для явного копирования перед reload; повреждённый server snapshot не загружается и не перезаписывается автоматически.

Карточка принята владельцем переходом к следующему этапу 2026-09-13. Bindings, semantic edges, realtime/CRDT, restore UI и Work Item projections остаются вне I0.5.

Изменения Plane fork зафиксированы локальным commit `53988697a8`; push не выполнялся.

## Rollback

Выключить Canvas flag. Additive tables остаются; versions не удаляются. Destructive down migration не выполняется на среде с данными.

## Stop rules

- permission mapping Plane неоднозначен;
- save требует изменения core Plane tables;
- snapshot размер не ограничен;
- stale write может перезаписать current version.
