# G1.3 — Git write actions и draft PR с подтверждением

## Пользовательский результат

РП или разрешённый участник создаёт branch и draft pull request из PPM после просмотра точного preview. Повторное
подтверждение не создаёт дубликат.

## Зависимости и входы

- G1.1 accepted;
- собственные project-scoped approve/reject, idempotency и audit Git-раздела;
- provider write-permission ADR;
- proposed decision: [двухэтапный branch → commit/push → draft PR](<../Решение — Двухэтапный Git write flow branch и draft PR.md>);
- документы 10 и 13.

## Scope

- preview repository/base/head/name/title/body/Work Item;
- capability check и explicit approve/reject;
- idempotent create branch и draft PR;
- provider error/rate-limit/conflict handling;
- link к Work Item и Canvas context;
- audit инициатора, provider identity, request и outcome;
- revoke/cancel behavior.

## Не входит

- автоматический merge;
- force push и изменение protected branch;
- хранение private SSH key;
- произвольное выполнение shell/git command;
- создание PR без подтверждения.

## Реализовано 2026-09-21 — безопасный preview/decision slice

- добавлена project-scoped модель Git write action со строгими статусами, source versions и audit trail;
- РП и разрешённый участник могут подготовить точный preview repository/base/head/title/body/Work Item;
- один `client_operation_id` идемпотентен, а повтор с изменённым payload возвращает явный конфликт;
- approve/reject выполняются отдельно и повторно проверяют актуальность repository, connection и Work Item;
- изменение источника переводит действие в `conflict` без обращения к provider write API;
- гость не может создавать или подтверждать write action; global admin сохраняет project-scoped доступ;
- интерфейс раздела «Код» показывает форму, точный preview, историю последних действий и безопасные статусы;
- `PPM_GIT_WRITE_ENABLED=0` установлен по умолчанию; текущий slice не создаёт ветку или PR и не умеет merge;
- GitHub provider adapter умеет отдельно создать/replay ветку с `Contents: write` и draft PR с
  `Pull requests: write`, обнаруживает чужую ветку и запрещает PR без нового commit; эти методы не подключены к
  пользовательской apply-команде;
- overview и список write actions возвращают безопасную диагностику готовности: утверждён ли flow, включён ли
  внешний write-флаг, какие permissions есть у каждой connection и каких scopes не хватает;
- раздел «Код» показывает эту диагностику по каждому repository и явно объясняет все blockers; apply остаётся
  недоступен даже при наличии scopes, пока владелец не утвердит flow и не появится отдельный endpoint;
- РП или global admin может кнопкой «Проверить права» безопасно перечитать актуальную установку через GitHub App
  API; PPM обновляет permissions установки и project connections, не создавая веток, commit или PR, и пишет audit;
- webhook `new_permissions_accepted` автоматически обновляет permissions всех активных project connections, а
  `unsuspend` восстанавливает только ранее приостановленные connections; disconnected/revoked не активируются;
- интерфейс показывает пошаговую инструкцию GitHub `Permissions & events` и отдельно напоминает, что выдача
  scopes не создаёт ветку или PR без подтверждения в PPM;
- локальная миграция применена; полный `ppm_git` contract suite — 52 теста, web type/lint/format/build и browser
  smoke прошли.

## Реализовано 2026-09-27 — двухэтапный apply за флагом (RC, линия C)

Решение владельца 2026-09-26: два подтверждения, живой GitHub не проверяется (нет тестового репозитория и прав App)
— поведение закреплено контрактами с подставным GitHub; живой E2E — известное ограничение RC. Подробности —
[решение о двухэтапном flow](<../Решение — Двухэтапный Git write flow branch и draft PR.md>) (статус `accepted`).

- типы действий `create_branch` и `create_draft_pr` (второе ссылается на применённое первое), миграция
  `ppm_git 0007` (обратимая; старые открытые одношаговые предложения закрыты кодом `GIT_WRITE_FLOW_SUPERSEDED`);
- preview ветки читает GitHub и фиксирует точный base SHA, занятое имя отклоняет; preview черновика PR — base/head
  SHA, сводка коммитов, отказ без новых коммитов и при существующем PR; готовность шага 2 видна по webhook;
- `apply` (`APPLYING` + fencing-токен, аренда, фиксация только владельцем токена, повтор после `applied` без
  обращения к GitHub; существующая ветка/PR признаётся «своей» только на повторной попытке) и `cancel`;
- 401/403/404/409/422/429, отозванный токен и установка, нехватка прав, rulesets, неподдерживаемый draft PR —
  видимый `failed`/`conflict` без скрытого повтора; повтор — явный и не раньше `retry_after`;
- созданные ветка и PR сохраняются как Git objects и связываются с задачей (попадают на Холст); аудит каждого шага;
- `PPM_GIT_WRITE_ENABLED=0` по умолчанию: preview/approve/cancel/аудит работают, apply — отказ «запись выключена
  администратором», раздел «Код» показывает ручные команды и ссылку на сравнение веток;
- «Код»: оба шага с русскими подписями, кнопки только у РП/участников (и global admin), список последних действий;
- проверки: `ppm_git` 78 passed (13 сценариев потока + провайдер + миграция), мутационная проверка 8/8, web vitest
  и tsc/oxlint/oxfmt — см. отчёт `.superpowers/sdd/2026-09-26-ppm-rc/task-RCC-report.md`.

## Критерии приёмки

1. Preview однозначно показывает, что будет создано и где.
2. Без approve provider write API не вызывается.
3. Повтор с тем же idempotency key возвращает исходный результат.
4. Недостаточная provider/project permission даёт отказ без частичного скрытого действия.
5. Созданный draft PR связан с Work Item и canonical provider URL.
6. Merge остаётся у Git provider и не запускается из PPM.

## Проверки

- approve/reject/replay;
- concurrent branch name conflict;
- revoked token и provider rate limit;
- protected branch negative suite;
- audit completeness;
- E2E Work Item → preview → branch → draft PR.

## Rollback

Выключить Git write-actions feature и отозвать write scopes. Read sync и ранее созданные provider objects сохраняются.
