# I1.3 — Проектные агенты и approval actions

Решение владельца от 2026-09-23: проектные агенты исключены из текущей
очереди PPM и release gate. Реализованный код и отчёт ниже сохраняются
как история; новые этапы этой карточки не планируются.

## Пользовательский результат

Project Reporter, Work Decomposer, Knowledge Librarian и Relationship Analyst готовят проверяемые предложения, а пользователь применяет выбранные изменения после просмотра diff.

## Зависимости

- I1.2;
- документы 08/12/13/16;
- approved model/retention policy.

## Scope

- agent kind registry;
- strict tool/action schemas;
- agent run/action/citation models;
- read-only tools;
- proposal generation;
- preview UI/selective approve/reject;
- permission/source precondition recheck;
- idempotent apply;
- cancel/timeouts/audit;
- four named agents.

## Не входит

- unattended autonomous mode;
- Git Reviewer until G1.2;
- merge/delete repository;
- mass changes without per-action visibility;
- arbitrary shell/browser tools.

## Порядок реализации

1. Добавить schemas/models/migrations.
2. Создать tool registry deny-by-default.
3. Реализовать read-only context tools.
4. Реализовать proposal-only actions.
5. Создать preview/diff UI.
6. Реализовать approve endpoint с permissions/preconditions.
7. Реализовать idempotent appliers.
8. Добавить cancel/retry/audit.
9. Реализовать агентов по одному, начиная Project Reporter.
10. Прогнать adversarial/duplicate/stale tests.

## Критерии приёмки

1. Read-only tool не мутирует data.
2. Proposal не применён до approve.
3. Пользователь видит каждое действие и source.
4. Недоступное право/изменённая version блокирует apply.
5. Повторный approve не дублирует object.
6. Partial batch прозрачен.
7. Prompt injection не расширяет tools.
8. Audit связывает run, sources, approval и result.

## Проверки

- tool/action schema contracts;
- permission/precondition/idempotency;
- cancel/retry/timeouts;
- prompt injection;
- source citations;
- four agent golden suites;
- no-provider/manual fallback.

## Реализовано 2026-09-21 — безопасный foundation

- добавлены project-scoped модели и миграция для agent run, proposal action, citation и audit event;
- зарегистрированы четыре утверждённых типа агента: Project Reporter, Work Decomposer, Knowledge Librarian и
  Relationship Analyst;
- создан deny-by-default tool registry со строгими JSON-схемами: агент видит только свои read/propose tools, а
  apply tools нельзя вызвать из agent run;
- capabilities формируются только сервером; browser/input не может добавить `project_id`, роль или инструмент;
- полный browser request не сохраняется: run хранит SHA-256 fingerprint, безопасный context, версию policy и
  только нормализованные allowlisted параметры своего типа агента, необходимые для восстановления очереди;
- proposal action содержит отдельные payload, понятный preview, source versions и idempotency key;
- approve фиксирует решение и audit, но сам по себе не выполняет canonical mutation; для поддерживаемых типов
  действий применяется отдельная явная команда после подтверждения;
- перед approve повторно проверяются project scope, доступность и версия каждого source; stale/foreign source
  блокирует подтверждение;
- добавлен project-scoped read-only endpoint реестра агентов. `PPM_AGENTS_WRITE_ENABLED=0` остаётся значением по
  умолчанию и не позволяет перейти к apply;
- реализован локальный deterministic runner «Сводка проекта»: он читает только canonical Work Items текущего
  проекта, считает состояния, завершённые, просроченные и рисковые задачи, а citations прикрепляет только к
  актуальным `ready`-источникам после повторной проверки canonical source version;
- добавлены project-scoped API создания, списка и чтения собственных agent runs; сохранённые параметры остаются
  server-only и не попадают в serializer, а повторный `client_operation_id` идемпотентен;
- в панели Мозга проекта появился read-only preview «Сводка проекта» с четырьмя метриками, важными задачами,
  предупреждением о неподтверждённых источниках и ссылками на версионированные подтверждения;
- реализован deterministic runner «Декомпозиция работы»: пользователь задаёт цель и выбирает актуальную задачу,
  агент создаёт три независимых proposal actions — по одному черновику с описанием и критериями приёмки;
- добавлен preview UI с каждым будущим Work Item, исходной задачей и закреплённой версией источника;
- selective approve/reject защищён правом редактирования проекта, идемпотентен и повторно проверяет source
  preconditions; принятие фиксирует решение и audit, а отдельная команда применения создаёт только выбранные
  canonical Work Items;
- добавлен прозрачный run-level partial batch: РП может принять или отклонить выбранную часть действий,
  сохранить её атомарно и вернуться к оставшимся; summary показывает `approved`, `rejected`, `remaining`,
  `partial` и `review_complete`, повтор той же операции не создаёт новый audit event;
- реализован deterministic runner «Библиотекарь знаний»: он принимает тему и один актуальный Markdown-источник
  текущего проекта, повторно проверяет его версию и формирует структурированный Markdown-черновик с цитатой и
  явным чек-листом фактчекинга;
- preview «Библиотекаря знаний» показывает будущую заметку, исходный материал и версию; approve/reject фиксирует
  решение, но не создаёт и не изменяет Vault-файл;
- реализован deterministic runner «Аналитик связей»: он требует ровно два выбранных объекта одного Холста,
  сверяет их с текущим snapshot и активными project-scoped bindings, а затем предлагает типизированную semantic
  edge с основанием и citations;
- preview «Аналитика связей» показывает направление, тип и объяснение связи; approve/reject фиксирует решение,
  но не создаёт Canvas semantic edge;
- добавлен project-scoped cancel: собственный queued/running/awaiting run отменяется идемпотентно, все ещё
  непринятые actions получают статус `cancelled`, canonical data не изменяются, а принятое предложение отменить
  нельзя;
- добавлен retry для ошибочных, отменённых и отклонённых запусков: клиент повторно передаёт исходные параметры,
  сервер сверяет их fingerprint, требует новый operation id и связывает обе попытки audit events;
- в UI появился явный блок управления запуском с объяснением последствий, кнопками «Отменить запуск» и
  «Повторить» и отдельными статусами отмены;
- добавлен терминальный статус `timed_out` для зависших `queued`/`running` запусков; безопасный лимит по умолчанию
  равен 120 секундам и настраивается в диапазоне 30–3600 секунд;
- фоновая Celery-проверка раз в минуту и project-scoped чтение запусков переводят просроченную попытку в
  `timed_out`, отменяют только неприменённые proposal actions и фиксируют отдельные audit events;
- запуски `awaiting_approval` намеренно не истекают: пользователь может вернуться к решению позже; поздний worker
  не может перезаписать уже завершённый по лимиту run;
- UI восстанавливает последний `timed_out` run после reload, объясняет отсутствие canonical mutation и предлагает
  «Запустить заново»; если исходные параметры нельзя восстановить из безопасного результата, пользователь
  возвращается к форме, потому что полный prompt в PPM не хранится;
- выдача источников при большом Git-индексе теперь ставит Work Items и Vault выше code sources, а UI не
  отрисовывает сотни удалённых источников;
- миграция `ppm_brain.0006_agent_foundation` применена к локальному окружению без изменения существующих данных;
- additive migration `ppm_brain.0007_agent_run_timed_out` применена к локальному окружению без изменения
  canonical данных проекта.

## Реализовано 2026-09-21 — безопасные canonical appliers

- для принятых действий Work Decomposer добавлен отдельный endpoint применения; простое сохранение решения всё
  ещё не изменяет проект;
- интерфейс показывает самостоятельную кнопку «Создать принятые задачи» и до нажатия явно объясняет последствия;
- создаются только перечисленные пользователем действия со статусом `approved`; отклонённые, ожидающие решения и
  чужие действия блокируются;
- непосредственно перед записью повторно проверяются project scope, права, доступность и версия исходной задачи;
  изменившийся источник переводит действие в видимый статус `conflict` без создания Work Item;
- пакет применяется атомарно, повторный запрос возвращает уже созданный результат и не дублирует задачи;
- результат каждого действия хранит идентификатор, название и внутреннюю ссылку созданного Work Item; run summary
  показывает факт canonical mutation и список применённых action id;
- создание доступно РП/редактору проекта, но запрещено обычному участнику без права редактирования;
- локальная тестовая сборка включает `PPM_AGENTS_WRITE_ENABLED=1`; production/default по-прежнему закрыт
  (`0`) и требует отдельного решения перед развёртыванием;
- каждое начало и завершение применения, а также конфликт фиксируются в project-scoped audit.
- для принятого предложения Knowledge Librarian добавлено отдельное создание нового Markdown-файла в
  «Хранилище»; существующие файлы не перезаписываются, одинаковое имя даёт видимый конфликт, а повторный запрос
  не создаёт дубликат;
- результат создания заметки сохраняет идентификатор, имя, версию и внутреннюю ссылку на файл;
- для принятого предложения Relationship Analyst добавлено отдельное создание подтверждённой semantic edge на
  выбранной доске Холста; перед записью повторно проверяются проект, доска, её версия и оба объекта;
- изменившаяся версия доски или отсутствующий объект переводят действие в видимый конфликт без частичной записи;
- созданная связь сразу получает статус `confirmed`, происхождение `agent`, ссылку на доску и полный audit trail;
- три локальных canonical applier используют один project-scoped endpoint, общий write-флаг и одинаковую модель
  `preview → approve/reject → отдельное apply`.
- создание всех четырёх агентов доступно через дополнительный project-scoped POST/SSE endpoint: новый run
  последовательно отдаёт `queued`, `running` и финальный снимок, replay по тому же operation id не запускает
  runner повторно, а failure event не раскрывает traceback; прежний JSON endpoint сохранён;
- потоковый runner переведён в долговечную Celery/RabbitMQ-очередь: API сохраняет нормализованный allowlisted
  input, ставит run в очередь и только наблюдает за его состоянием. Задание переживает restart API, а атомарный
  claim не позволяет повторной доставке выполнить один run дважды;
- минутная recovery-задача повторно ставит оставшиеся `queued` runs в очередь; browser получает отдельные
  progress-события локальных read/propose вызовов только с устойчивым `call_id`, временем, именем, режимом,
  статусом и числом результатов. Payload, prompt, actor, tokens и произвольные metadata не передаются;
- recovery-задача также подхватывает `running` run после истечения worker lease; новый fencing token блокирует
  записи от устаревшей попытки, детерминированные action keys и idempotent citations не создают дубли, а после
  трёх аварийных попыток запуск безопасно получает `timed_out`;
- browser видит только число попыток и понятное сообщение «Исполнение восстановлено»; lease token, task id и
  время аренды остаются server-only. Миграция `ppm_brain.0009_agent_run_worker_lease` применена локально;
- фоновый heartbeat живого task продлевает только актуальную fenced-аренду; устаревшая попытка не может продлить
  lease после reassignment;
- панель показывает текущий/последний шаг и не допускает наложения второго запуска на активный агентский run.
- после reload браузера панель приоритетно находит active run и продолжает project-scoped detail polling до
  terminal-снимка; последний завершённый tool step восстанавливается из redacted audit, а при отсутствии active
  run показывается действительно самый свежий запуск.
- повтор failed/timed_out/cancelled/rejected run теперь доступен и через отдельный project-scoped POST/SSE
  endpoint: новый linked run сразу появляется в панели, отдаёт тот же browser-safe progress и допускает отмену;
  retry replay идемпотентен, JSON endpoint сохранён для совместимости.

## Rollback

Выключить `PPM_AGENTS_WRITE_ENABLED`; read-only Project Q&A сохраняется. Applied canonical changes не откатываются автоматически.
