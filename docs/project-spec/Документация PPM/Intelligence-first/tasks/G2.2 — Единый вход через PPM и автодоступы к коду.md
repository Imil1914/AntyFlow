# G2.2 — Единый вход через PPM и автодоступы к коду

## Пользовательский результат

Человека заводят только в PPM. На Git-сервере он входит кнопкой «Войти через PPM», а доступ к коду следует за
проектами PPM. Добавили в проект — видит код проекта, убрали — доступ пропал, отключили в PPM — не может войти и
в Git. Администраторы PPM — администраторы Git-сервера. Руководитель проекта сам подключает репозитории своего
проекта.

## Решение владельца (2026-09-29)

Владелец выбрал G2.2 на «ночь и день» после RC.2 («Единый вход и доступы (G2.2) (Рекомендую)»). Как и в G2.1 —
«делай до конца»: спецификация и план записываются в документацию, работа идёт без промежуточных согласований,
коммиты локальные, без push. Отложено владельцем 2026-09-28 из G2.1 ради срока (объём «Быстрый»); техническая
основа — [Решение — Forgejo как собственный Git-сервер PPM](<../Решение — Forgejo как собственный Git-сервер PPM.md>),
альтернатива 4.

## Основание (проверено 2026-09-29)

Исследования: `.superpowers/sdd/2026-09-29-g22-sso/research/forgejo-facts.md` (исходники Forgejo v15.0.9 + проба
на живом Forgejo 15 с поддельным OIDC-провайдером) и `…/research/ppm-facts.md` (код PPM). Главное:

- Учётка, созданная через admin API с `source_id` (источник входа PPM) и `login_name` = `sub` **без пароля**,
  находится Forgejo при первом входе через OIDC сразу — без связывания учёток. Обязательно
  `"must_change_password": false`, иначе вход, API и git ломаются. Уникальность пары (`source_id`, `login_name`)
  Forgejo не проверяет — её обеспечивает PPM (поиск перед созданием). Вход не обновляет имя и почту — только `PATCH`.
- Forgejo не проверяет подпись ID token, но требует `iss` = `issuer` из discovery, `aud` = client_id, `exp`
  (без него — ошибка 500) и тот же `sub` в userinfo. PKCE S256 отправляется всегда, кроме первого входа после
  регистрации источника. Клиент аутентифицируется `client_secret_basic` (секрет — без спецсимволов). Discovery можно
  отдавать по внутреннему адресу при публичном `issuer`.
- `prohibit_login` мгновенно отрезает веб (и открытые сессии), API, git по HTTPS и SSH.
- `--admin-group`/`--group-team-map` источника перезаписывают флаги при каждом входе и не действуют на токены и SSH
  без входа — права ведёт PPM через API. `ENABLE_AUTO_REGISTRATION=false` (одного `DISABLE_REGISTRATION` мало),
  форма пароля прячется `ENABLE_INTERNAL_SIGNIN=false`; `ENABLE_BASIC_AUTHENTICATION` остаётся включённым (на нём
  выпуск и отзыв токенов `git-bootstrap`).
- `add-oauth` скачивает discovery в момент вызова; изменения источника видны вебу Forgejo только после рестарта.
- Admin sudo работает: `GET /api/v1/user/repos` с заголовком `Sudo: <имя>` отдаёт репозитории человека с правами.
  Прямая ссылка `https://git.<домен>/user/oauth2/PPM?redirect_to=/<орг>/<репозиторий>` — вход в один клик.
- В PPM: Django 5.2, PyJWT и cryptography уже есть, django-oauth-toolkit и jwcrypto — нет. `/auth/*` Caddy уже
  отдаёт API, и там видна обычная сессия PPM. Штатный `next_path` **не умеет** вернуть человека на серверную
  страницу после входа (подставляется без кодирования, последний шаг — клиентский `router.push`). Глобальный
  администратор PPM — `PpmGlobalAdmin` / `is_ppm_global_admin`. Сигналов на членство нет — изменения делают
  представления. Роли: 20 администратор, 15 участник, 5 гость. Администратор пространства не видит приватные проекты
  без членства.

## Scope

### A. PPM — OpenID Connect-провайдер для Git-сервера
- **R1.** Библиотеки `django-oauth-toolkit` 3.x и `jwcrypto` (закреплённые версии). Новое приложение
  `plane.ppm_oidc`; таблицы OAuth2 — в базе PPM. Настройки: ключ подписи RS256 только из окружения
  (`PPM_OIDC_PRIVATE_KEY`, не в базе → не в бэкапах), `issuer` = `${PPM_PUBLIC_URL}/auth/oidc`, области
  `openid profile email groups`, короткие сроки (код — 60 с, access и ID token — 5 мин, refresh — 1 ч), просроченные
  токены удаляются ежедневно.
- **R2.** Точки под `/auth/oidc/` (Caddy уже ведёт `/auth/*` в API): `authorize/`, `token/`, `userinfo/`, `jwks/`,
  `.well-known/openid-configuration` — публичные адреса. Для Forgejo — внутренний discovery
  `/auth/oidc/internal/.well-known/openid-configuration`: тот же `issuer` и `authorization_endpoint` (публичные, их
  открывает браузер), а `token`, `userinfo`, `jwks` — на внутреннем адресе API (`http://api:8000`). Снаружи Caddy
  отвечает на `/auth/oidc/internal/*` кодом 404. Выход (logout), revoke и introspect не публикуются.
- **R3.** Ровно один клиент — Git-сервер: `client_id` из `PPM_OIDC_CLIENT_ID` (по умолчанию `forgejo`), секрет из
  `PPM_OIDC_CLIENT_SECRET` (в базе — только хэш), конфиденциальный, grant «authorization code», redirect URI строго
  `${PPM_GIT_PUBLIC_URL}/user/oauth2/PPM/callback`, RS256, без экрана согласия (доверенное приложение). Регистрация
  — идемпотентная команда `manage.py ppm_oidc_client --ensure` (приводит клиента к окружению, секреты не печатает).
  PKCE не обязателен для этого клиента, но если прислан — проверяется (S256).
- **R4.** Утверждения: `sub` = UUID пользователя PPM (не меняется); `name` — отображаемое имя (иначе имя и фамилия);
  `email`, `email_verified: true`; `nickname` и `preferred_username` — имя на Git-сервере, назначенное PPM (R10);
  `groups` — `["ppm-admins"]` для действующих глобальных администраторов (справочно — права ведёт синхронизация).
  В ID token всегда `iss`, `aud`, `exp`, `iat`, `auth_time`; `sub` в userinfo совпадает.
- **R5.** Войти могут только активные пользователи-люди (не боты) с почтой; остальным — `access_denied` (Forgejo
  показывает ошибку входа). Отключение пользователя в PPM делает недействительными его выданные токены Git-сервера.
- **R6. Возврат после входа.** Анонимный `authorize/` сохраняет запрос в кэше под одноразовым случайным id
  (10 мин) и отправляет на вход PPM с `next_path=/auth/oidc/continue/<id>/` (простой путь без query — проходит
  штатную проверку). Web для `next_path`, начинающегося с `/auth/oidc/`, делает полную навигацию браузера
  (`window.location.assign`), а не `router.push`, — во всех местах, где читается `next_path` (обёртка авторизации,
  формы входа). `continue/<id>/` (с сессией) один раз воспроизводит сохранённый запрос; устаревший или чужой id —
  понятная страница по-русски: «Ссылка для входа устарела. Вернитесь на Git-сервер и нажмите «Войти через PPM» ещё
  раз» со ссылкой. Уже вошедший в PPM человек проходит `authorize/` сразу, без ввода данных.
- **R7. Защита.** Ограничение частоты на `token/` и `continue/`; ошибки не раскрывают причин другим клиентам;
  коды, токены, секрет клиента и ключ не попадают в логи, аудит и ответы API; ротация ключа подписи (старый ключ
  публикуется в JWKS до истечения токенов) и секрета клиента описаны в RUNBOOK.

### B. Учётки и права на Git-сервере
- **R8. Служебный токен администрирования** `PPM_FORGEJO_ADMIN_TOKEN` (`ppm-bot`, области
  `write:admin,write:organization,read:repository,read:user`) — только для модуля доступов; токен провайдера на
  чтение остаётся как есть. Id источника входа «PPM» — `PPM_FORGEJO_SSO_SOURCE_ID` (записывает `git-bootstrap`).
- **R9. Учётка в момент входа.** Когда Git-сервер обменивает код входа на токены, PPM до выдачи токенов обеспечивает
  учётку человека: ищет по (`source_id`, `login_name` = `sub`); нет — создаёт (`POST /admin/users`: `source_id`,
  `login_name` = `sub`, имя из R10, почта, полное имя, `must_change_password: false`, без пароля). Имя и почта
  сверяются `PATCH`. Локальные учётки Forgejo (режим «Быстрый») **не перенимаются**: у них остаются свои пароли,
  токены и SSH-ключи, которые PPM отозвать не может, а почту в Forgejo можно указать любую (ревью безопасности
  2026-09-29); такие учётки остаются как есть, RUNBOOK описывает, как их пересмотреть при включении единого входа.
  Затем применяются доступы этого человека (R12–R15) с ограничением времени (5 с): не успели — вход всё равно
  проходит, остаток — фоновой задачей. Учётку не удалось обеспечить — вход отклоняется, причина пишется в журнал и
  в центр администратора (R18).
- **R10. Имя на Git-сервере**: из части почты до `@` — строчные `a-z 0-9 . _ -`, не длиннее 39, не пустое и не
  зарезервированное; занято — `-2`, `-3`…; хранится в PPM и потом не меняется (по нему адреса личных репозиториев).
- **R11. Пространство → организация**: имя — slug пространства (приведённый к правилам Forgejo, ≤ 40), полное имя —
  название пространства, видимость — частная. Существующая организация с таким именем перенимается (с записью в
  аудит). Команду «Owners» PPM не трогает.
- **R12. Проект → команды по ролям** (создаются, когда нужны): `<КЛЮЧ>-admin` — «Администратор» (может создавать
  репозитории в организации) ← администратор проекта (20); `<КЛЮЧ>` — «Запись» ← участник (15); `<КЛЮЧ>-read` —
  «Чтение» ← гость (5). Разделы команд — через `units_map` (код, запросы на слияние, задачи, релизы, вики).
  Описание: «PPM: <роль> проекта «<название>». Состав ведёт PPM — не меняйте вручную». Смена ключа проекта
  переименовывает команды; удалённый проект — команды удаляются (репозитории остаются в организации).
- **R13. Репозитории проекта** = активные подключения Forgejo этого проекта, лежащие в организации его
  пространства: добавляются во все команды проекта, при отключении — убираются. Репозиторий вне организации
  (личный, чужая организация) — доступ не ведётся, в статусе (R18) предупреждение «Доступ к <репозиторий>
  настраивается вручную: он вне организации пространства».
- **R14. Глобальные администраторы PPM** → `admin: true` у своих учёток на Git-сервере; отзыв → `false`. Учётки,
  которые PPM не создавал (`ppm-bot`, аварийный администратор, локальные учётки режима «Быстрый»), PPM не трогает
  никогда — ни флаг администратора, ни вход, ни членство в командах.
- **R15. Уход и отключение**: исключён из проекта или пространства → убран из его команд; пользователь отключён
  или удалён → `prohibit_login: true` и убран из всех команд PPM; снова активен → вход и доступы восстанавливаются.
- **R15a. Отключение пользователя администратором** (добавлено 2026-09-29 по итогам сквозной проверки: способа
  отключить человека в PPM не было): в центре администратора у пользователя — «Отключить» / «Включить» (только
  глобальный администратор; нельзя себя, глобальных администраторов и администраторов инстанса). Отключённый не
  может войти в PPM (вход не включает его обратно), его сессии завершаются, в Git-сервере срабатывает R15; аудит.
- **R16. Когда синхронизируется**: изменения членства, ролей, пользователей, глобальных администраторов, подключений,
  проектов и пространств → отложенная (≈5 с, со склейкой) задача по затронутому кругу; полная сверка каждые
  10 минут исправляет расхождения (ручные правки команд PPM в Forgejo, массовые изменения без сигналов). Сверка
  работает только с людьми, у которых уже есть учётка на Git-сервере (появляется при первом входе, R9), —
  лишних учёток не создаёт. Все изменения — в аудит `PpmGitAudit` (`forgejo.access.*`), без секретов.

### C. Руководитель проекта подключает репозитории
- **R17.** Администратор проекта (20) видит и подключает репозитории Forgejo из организации своего пространства,
  на которые у его учётки есть права администратора (создал сам или через команду `<КЛЮЧ>-admin`), — список через
  admin sudo. Нет учётки на Git-сервере — подсказка «Сначала войдите на Git-сервер кнопкой «Войти через PPM» — здесь
  появятся ваши репозитории». Глобальный администратор, как в G2.1, подключает любой репозиторий. Отключает тот, кто
  может подключать (при едином входе — и администратор своего проекта).

### D. Центр администратора
- **R18.** Вкладка «Git-сервер» (только глобальные администраторы): Git-сервер настроен / отвечает, единый вход
  включён, последняя полная сверка (время, длительность, итог), числа (учётки, организации, команды, репозитории под
  управлением PPM), последние проблемы (до 50: кто/что, понятный текст, время), кнопка «Синхронизировать сейчас»,
  ссылка на панель администратора Forgejo. Без секретов.
- **R19.** API статуса и запуска сверки — только глобальному администратору; ошибки синхронизации — по-русски.

### E. Web
- **R20.** Полная навигация для `next_path` вида `/auth/oidc/…` (R6) с тестом.
- **R21.** «Код»: подключение репозитория администратором проекта (R17); у карточек репозиториев Git-сервера —
  «Открыть на Git-сервере» через вход в один клик (`/user/oauth2/PPM?redirect_to=/<орг>/<репозиторий>`); в «Как
  скачать код» — «Ваше имя на Git-сервере: <имя>» и подсказка про токен для HTTPS; тем, у кого учётки ещё нет, —
  «Войдите на Git-сервер кнопкой «Войти через PPM»».
- **R22.** Строки по-русски, облик v1 и v2 не ломается, vitest/tsc/oxlint — в пределах базы.

### F. Комплект развёртывания
- **R23.** `ppm-env.sh`: ключи единого входа (`PPM_GIT_SSO_ENABLED`, `PPM_GIT_LOCAL_SIGNIN`, `PPM_OIDC_CLIENT_ID`,
  секреты `PPM_OIDC_PRIVATE_KEY`, `PPM_OIDC_CLIENT_SECRET`, `PPM_FORGEJO_ADMIN_TOKEN`, `PPM_FORGEJO_SSO_SOURCE_ID`)
  — в `init` для новых установок и командой `add-sso` для существующих (остальные строки файла не меняются); `check`
  их проверяет; секреты генерируются и не печатаются.
- **R24.** Compose: API и фоновые задачи получают ключи OIDC и токен администрирования; Forgejo —
  `ENABLE_AUTO_REGISTRATION=false`, `ACCOUNT_LINKING=disabled`, `USERNAME=nickname`, `UPDATE_AVATAR=false`,
  `ENABLE_INTERNAL_SIGNIN` = `PPM_GIT_LOCAL_SIGNIN` (по умолчанию выключено при едином входе); Caddy закрывает
  `/auth/oidc/internal/*` снаружи.
- **R25.** `git-bootstrap` при включённом едином входе: клиент OIDC в PPM (`ppm_oidc_client --ensure`) → источник
  «PPM» в Forgejo (`add-oauth` с внутренним discovery и `--skip-local-2fa`; при расхождении — `update-oauth`; затем
  рестарт Forgejo) → id источника в окружение → токен администрирования (тот же безопасный порядок выпуска, проверки
  и отзыва, `--rotate-token` меняет оба токена) → первая полная сверка. Повтор ничего не ломает.
- **R26.** Аварийный вход: `PPM_GIT_LOCAL_SIGNIN=1` + `up` возвращает форму пароля (для учётки `git-admin`);
  `PPM_GIT_SSO_ENABLED=0` возвращает режим G2.1 «Быстрый» (учётки остаются, синхронизация выключена).
- **R27.** RUNBOOK §17: единый вход, автоматические доступы (и что ручные правки команд PPM откатываются), аварийный
  вход, ротация ключа, секрета и токенов, диагностика; п. 17.5 — что меняется при едином входе; `cli-checks.sh`
  покрывает новое. Бэкапы: нового нет (таблицы OAuth2 — в дампе PPM, секреты — только в окружении).

### G. Проверка
- **R28.** Тесты: поток OIDC (discovery публичный и внутренний, authorize с сессией и без, continue, token, userinfo,
  jwks, утверждения, неактивный/бот, чужой клиент и redirect URI, с PKCE и без), учётка при входе (поиск, перенятие,
  создание, `must_change_password`, сверка профиля, ошибки), синхронизация на поддельном Forgejo (организация, команды
  по ролям, участники, репозитории, отключение, администраторы, идемпотентность, ручные правки, переименование,
  удаление), сигналы и склейка, права администратора проекта на подключение, API статуса; web; комплект; регрессии
  `ppm_git` и GitHub целиком.
- **R29. Сквозная проверка** на одноразовом стеке с живым Forgejo 15: первичная настройка с единым входом → участник
  ROBOT нажимает «Войти через PPM» и сразу видит репозитории проекта → руководитель создаёт репозиторий в организации
  и подключает его в PPM → участник пушит, гость только читает, посторонний не видит → исключение из проекта убирает
  доступ, отключение пользователя — вход и git → глобальный администратор — администратор Forgejo → статус в центре
  администратора → аварийный вход → поиск секретов в логах → учения восстановления проходят.
- **R30.** Ревью безопасности: точки OIDC, выдача и хранение токенов, учётка при входе, токен администрирования,
  закрытие внутреннего discovery, логи.

## Не входит

- вход в PPM через Forgejo; внешние провайдеры учёток (Keycloak, Authentik); общий выход (single logout);
- создание репозиториев из PPM (руководитель создаёт их в Forgejo — у его команды есть это право);
- права на уровне веток, синхронизация SSH-ключей, группы и команды Forgejo вне модели PPM;
- запись в Git из PPM для Forgejo (ветка и черновой PR) — отдельная доработка.

## Критерии приёмки

1. Новый участник проекта входит в Forgejo кнопкой «Войти через PPM» без отдельного пароля и сразу видит код
   проекта.
2. Исключение из проекта убирает доступ к коду, отключение пользователя — вход в Forgejo и git, в пределах одной
   сверки (обычно — за секунды).
3. Токены и ключи подписи не попадают в браузер, логи и резервные копии в открытом виде.
4. Руководитель проекта сам подключает репозиторий своего проекта.
5. Глобальные администраторы PPM — администраторы Git-сервера; состояние синхронизации видно в центре
   администратора.
6. Аварийный вход администратора Forgejo по паролю включается одной настройкой.

## Rollback

`PPM_GIT_SSO_ENABLED=0` → режим G2.1: форма пароля Forgejo возвращается, синхронизация выключена, учётки, команды
и история остаются; клиент OIDC отключается (`ppm_oidc_client --disable`). Таблицы OAuth2 удаляются только
отдельным подтверждённым действием.
