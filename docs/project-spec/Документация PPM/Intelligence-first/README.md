# PPM Intelligence-first — каноническое ТЗ v12

Решение владельца от 2026-09-23: текущий план PPM не включает
AI-провайдеров, генеративный Ask Project, AI-чат, проектных агентов и внешние AI-источники.
Реализованные ранее фрагменты сохранены как история; они не блокируют Git,
совместный Холст и выпуск. Действующий объём — Plane, Canvas, Vault,
Project Brain без AI-модели, Git и эксплуатация. См. [мастер-план](<22 — Полный план завершения PPM.md>).

## Статус документа

Эта папка — единственная исполнительная редакция ТЗ PPM после решения владельца объединить:

1. функциональный движок Plane Community;
2. полностью собственный интерфейс и дизайн-язык AntyFlow;
3. визуальный «Мозг проекта» на базе холста;
4. Project Vault — файловую базу знаний в стиле Obsidian;
5. изолированный RAG и граф знаний каждого проекта;
6. интегрированный Git-контур для VS Code, Codex, commit, branch и pull request.

Предыдущие редакции сохранены как история:

- [web-first v1](<../README.md>);
- [Plane-first v2](<../Plane-first/README.md>).

## Продукт в одном предложении

**PPM — AntyFlow-first система проекта, в которой Plane выполняет роль движка управления работой, Project Vault хранит файлы и знания, Canvas связывает всё в граф, Project Brain помогает искать проверяемые источники, а Git-контур соединяет задачи с кодом и pull request.**

## Архитектурная формула

```text
Plane-powered        — готовая предметная логика проектов и задач
AntyFlow-faced       — собственная оболочка и визуальный язык
Vault-backed         — файлы и Markdown как переносимые артефакты
Graph/RAG-assisted   — отдельный интеллект каждого проекта
Git-connected        — стандартный цикл разработки без самописного Git
```

## Неподвижные правила

1. Пользователь не видит продукт Plane: он видит PPM/AntyFlow.
2. Plane не переписывается с нуля и остаётся источником истины для пользователей, проектов и Work Items.
3. Canvas повторяет опыт AntyFlow; Kanban/backlog работают как представления Plane Work Items без второй базы задач.
4. Project Vault — источник истины для файловой библиотеки и Markdown-заметок проекта.
5. Plane Pages сохраняются как штатные совместные страницы, но отображаются вместе с Vault через единый раздел «Знания».
6. RAG-индекс производный: его можно удалить и полностью построить заново из источников.
7. У каждого проекта отдельное пространство индекса и графа; межпроектная утечка запрещена.
8. Код, ветки, commits и pull requests принадлежат Git provider, а не PPM.
9. Пользовательские Git write actions требуют preview, явного подтверждения и audit; AI-запись исключена из текущего плана.
10. Модификация Plane ведётся в контролируемом fork от закреплённого релиза `v1.4.2` с соблюдением AGPL-3.0.
11. У каждого проекта один общий Canvas и много общих досок.
12. Только protected global admin имеет сквозной доступ ко всем проектам; РП и участники ограничены membership.

### Исторический отчёт I1.3 (вне текущего плана)

Безопасный foundation [I1.3](<tasks/I1.3 — Проектные агенты и approval actions.md>) реализован без внешней модели:
deny-by-default registry, строгие schemas, project-scoped run/action/citation/audit records и stale-source check.
Все четыре локальных runner работают без внешней модели: «Сводка проекта» показывает метрики и риски,
«Декомпозиция работы» — три черновика задач, «Библиотекарь знаний» — Markdown-черновик из актуального материала
Хранилища, а «Аналитик связей» — типизированную связь между двумя выбранными объектами Холста. Все preview
используют версионированные источники и поддерживают role-safe approve/reject без canonical mutation. Для
декомпозиции реализован прозрачный partial batch: три независимых действия можно рассмотреть частично, а сводка
показывает принятое, отклонённое и оставшееся. Запуски можно отменять и идемпотентно повторять с теми же
параметрами; связь между попытками остаётся в аудите. Зависшие `queued`/`running` попытки автоматически получают
статус `timed_out`, неприменённые предложения отменяются, а `awaiting_approval` не истекает. UI восстанавливает
этот статус после reload и предлагает безопасный новый запуск без хранения исходного текста запроса. Три
локальных canonical applier уже готовы: создание выбранных Work Items, нового Markdown-файла Хранилища и
подтверждённой semantic edge. Внешняя модель и
[AF1.1](<tasks/AF1.1 — AI и service nodes AntyFlow в web.md>) исключены из действующего плана.

### Действующий Git-поток

[G1.3](<tasks/G1.3 — Git write actions и draft PR с подтверждением.md>) начата: раздел «Код» умеет подготовить
точный project-scoped preview ветки и draft PR, сохранить approve/reject, обнаружить устаревший источник и
вести audit без обращения к provider write API. Запись в GitHub выключена по умолчанию. Реальное создание ветки
и draft PR начнётся только после write-permission ADR; автоматический merge не входит в продукт. В разделе «Код»
уже доступна безопасная диагностика GitHub App: требуемые, текущие и отсутствующие permissions плюс причины,
по которым apply закрыт. Кнопка «Проверить права» сверяет её с актуальной установкой GitHub без provider write.
После принятия новых permissions GitHub webhook обновляет project connections автоматически, а UI показывает
точные шаги настройки.

### Исторический отчёт AF1.1 (вне текущего плана)

[AF1.1](<tasks/AF1.1 — AI и service nodes AntyFlow в web.md>) начата независимым web-native срезом без внешней
модели: найденные Project Brain источники сохраняются на общий Холст как versioned `search`-нода с точным
запросом, scope, retrieval mode, версиями и ссылками. Живой сценарий search → save → reload подтверждён в
тестовом проекте. Project Agent runs также сохраняются как versioned `orchestrator` snapshots со статусом,
предложенными действиями, applied-result links и citations, но без скрытых prompts и provider secrets.
Одна карточка соответствует одному `run_id`: более свежий статус обновляет её на месте, stale snapshot
игнорируется, а наблюдаемая хронология сохраняется после reload без дублирования нод.
К хронологии подключён redacted server audit trace с реальными timestamps. Служебные metadata, actor id, prompts
и tokens не покидают backend; чтение известного run id через другой проект возвращает project-scoped `404`.
Действия и их server audit steps можно явно разложить в отдельные `orchtask`/`orchcall` объекты общего Холста;
повторное разложение обновляет их по run/action/trace id и не создаёт дублей. Привязанные стрелки формируют
видимый граф `orchestrator → task → call`, сохраняются после reload и двигаются вместе с карточками. Если запуск
уже разложен, его review/audit автоматически обновляет граф даже после закрытия и повторного открытия панели.
Локальные исполнители также публикуют browser-safe telemetry фактических read/propose/apply tool calls. На Холст
попадают только allowlisted имя, режим, итог и число результатов; payload, prompts, actor id, tokens и служебные
metadata остаются на сервере. Read-only E2E «Сводки проекта» сохранил одну карточку запуска, четыре tool-call
шага и их стрелки после reload (`61 → 66` PPM-объектов) без изменения проекта.
Все сохраняемые service nodes теперь используют единый server-authored `service_run` passport: search,
question/answer и orchestrator одинаково фиксируют run id, статус, policy/provider/model и timestamps. Новый
поиск `I0.8` сохранил этот паспорт на общем Холсте и пережил reload (`66 → 67` объектов); старые карточки
остаются читаемыми без обязательной миграции.
Все четыре Project Agents теперь запускаются через project-scoped POST/SSE-поток: браузер получает один и тот
же run в состояниях `queued → running → final`, может показать отмену до завершения и безопасно обработать
redacted failure. Идемпотентный повтор возвращает существующий итог, старый JSON endpoint сохранён. Живая
read-only сводка прошла новым маршрутом без изменения задач и Холста. Локальные read/propose вызовы теперь
отдают отдельные безопасные progress-события: браузер видит только `call_id`, имя, режим, статус и число
результатов. UI сохраняет последний шаг после быстрого завершения и не запускает вторую операцию поверх активного
агента. Живой E2E показал «Чтение задачи → Выполнено · результатов: 1» и финальную сводку по 9 задачам;
production web build пройден. Восстановление после reload браузера затем закрыто: панель при открытии находит
активный run, показывает «Наблюдение восстановлено» и project-scoped polling доводит его до terminal-снимка.
Последний tool step восстанавливается из redacted audit; при отсутствии active run открывается самый свежий
запуск, а не старая ошибка. Живой E2E подтвердил reload → cancel без изменений проекта и состояние «Сводка
отменена». Следующий слой перевёл выполнение в долговечную Celery/RabbitMQ-очередь: queued run переживает
restart API, recovery возвращает его worker, а атомарный claim не допускает двойное исполнение. Следующий срез
добавил lease/fencing, heartbeat и восстановление после падения worker без дублей. Следующий срез завершил
security negative suite и добавил потоковый completion adapter с безопасным progress и cooperative cancel;
живая проверка внешнего provider остаётся закрыта до policy.
Повтор terminal-запуска также переведён на тот же project-scoped POST/SSE-helper: браузер получает новый
связанный `run_id`, безопасные tool progress и доступ к отмене, а replay одного operation id не создаёт дубль.
Прежний JSON retry endpoint сохранён. Живой повтор отменённого Reporter завершился новой сводкой `9 / 1 / 0 / 3`
и последним шагом чтения задачи без изменения задач или Холста.
Активный Answer run также больше не теряется после reload: API отдаёт только последние собственные запуски,
панель выбирает самый свежий активный процесс между Answer и Agent и снова подключается к Answer SSE с polling
fallback. Живой E2E подтвердил восстановление, stop и сохранение «Запрос остановлен» после второго reload.
Search и Answer теперь запускаются тем же browser-side service-stream parser, что и Project Agents: новые
POST/SSE endpoints сразу отдают `run_id`, безопасный progress и terminal snapshot, поддерживают остановку и
оставляют прежние JSON/create/events маршруты для совместимости. Живой streamed поиск и Answer через Celery
worker подтверждены. Provider readiness теперь требует явное egress-разрешение, версию принятой политики и
отдельный server-only ключ без fallback на legacy-настройки. Текущий Project Brain suite — 75 тестов, agent
foundation — 33, web suite — 50; внешний egress при проверках не включался.
AF1.2 начата board-scoped realtime presence foundation: ASGI/WebSocket и Redis разделяют комнаты по
workspace/project/board, session-auth и heartbeat закрывают чужой либо отозванный доступ, global-admin connect
аудируется, а web показывает состояние подключения и участников. Живой reconnect прошёл после чистой пересборки;
Canvas API — 69 тестов, web suite — 53. Shared mutations, удалённые курсоры и conflict/offline recovery ещё не
закрыты.
AI chat/provider часть не входит в действующую очередь.
