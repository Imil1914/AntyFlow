# Решение — Двухэтапный Git write flow: branch, затем draft PR

**Статус: принято владельцем 2026-09-26** (пакет решений RC, D4: «два подтверждения — сначала ветка без скрытого
коммита, затем черновик PR после первого коммита/push»). Реализовано в G1.3 (RC, линия C, 2026-09-27) за флагом
`PPM_GIT_WRITE_ENABLED`, который в RC **выключен по умолчанию**. Живая проверка на GitHub не проводилась (нет
тестового репозитория и прав App) — поведение закреплено контрактными тестами с подставным GitHub; живой E2E —
известное ограничение RC.

## Почему требуется решение

Первый preview G1.3 показывал branch и draft PR как одно предложение. Однако нормальный GitHub flow выглядит
так: создать branch, сделать и отправить commit, затем открыть pull request. Сразу после создания branch его head
совпадает с base; создавать скрытый пустой commit только ради PR небезопасно и не входит в подтверждённый preview.

Основание:

- [GitHub: quickstart for pull requests](https://docs.github.com/en/pull-requests/get-started/pull-request-quickstart)
  задаёт последовательность branch → changes/commit → pull request;
- [GitHub: создание Git reference](https://docs.github.com/en/rest/git/refs) требует repository permission
  `Contents: write`;
- [GitHub: создание pull request](https://docs.github.com/en/rest/pulls/pulls) требует repository permission
  `Pull requests: write`.

## Решение

Два явных подтверждаемых действия; каждое проходит отдельные **preview → approve → apply**.

### Действие 1 — создать branch (`create_branch`)

Preview читает GitHub (только чтение) и показывает repository, **точный base SHA**, имя новой branch, Work Item и
provider account; имя, уже занятое в GitHub, отклоняется сразу. Имена base и новой branch — только латинские буквы,
цифры и `. _ / -` плюс правила Git (без `..`, `//`, `@{`, без `-`/`/`/`.` в начале и `/`/`.`/`.lock` в конце, до
244 символов): такие имена безопасно подставлять в ручные команды в любом shell (POSIX, PowerShell, cmd); всё прочее
отклоняется на preview понятным сообщением. После approve отдельная команда apply создаёт
только новый ref ровно на показанном SHA. PPM не создаёт commit, не изменяет файлы, не делает force push и никогда
не двигает и не удаляет существующие ветки.

### Действие 2 — создать draft PR (`create_draft_pr`)

Доступно только после применённого действия 1. После первого commit/push PPM получает webhook/reconciliation и
помечает, что второй preview можно готовить; сам webhook никогда не запускает provider write. Preview заново читает
GitHub и показывает base/head SHA, сводку коммитов (до 20 + общее число), Work Item, PR title/body и provider
account. Без новых коммитов preview отклоняется (скрытого пустого commit нет); **открытый** PR для этих веток —
конфликт со ссылкой на него, закрытые/слитые PR (в том числе ранее созданные через PPM) не мешают и показываются
справочно. Название PR — до 256 символов (ограничение GitHub). Только новое approve и apply создают PR, всегда с
`draft: true`. В конец описания PPM добавляет невидимую в GitHub служебную отметку
`<!-- ppm-write-action:<id действия> -->` — она показана в предпросмотре и служит единственным доказательством, что PR
создан этим действием.

### Merge

Merge отсутствует во всех API, capability и UI PPM и выполняется только в GitHub.

## Минимальные права GitHub App

- `Metadata: read` — штатное обязательное чтение GitHub App;
- `Contents: write` — только создание нового branch ref;
- `Pull requests: write` — только создание draft PR;
- `Workflows: write`, `Administration: write`, `Issues: write` и merge permission не запрашивать.

Installation token запрашивается на каждый шаг только для выбранного repository и только с нужным scope
(`contents: write` для ветки; `contents: read` + `pull_requests: write` для PR; для preview — только чтение).
Токен не сохраняется, не логируется, не попадает в аудит и не передаётся browser.

## Preconditions, идемпотентность и fencing

- approve и apply повторно проверяют repository, Work Item и установку GitHub App из preview; фоновая синхронизация
  подключения (webhook/reconcile) preview не инвалидирует, переустановка App — инвалидирует (`conflict`);
- apply: в транзакции статус `approved` → `applying` с новым fencing-токеном и номером попытки; вызов GitHub —
  вне транзакции; результат фиксируется только владельцем актуального токена. Живой `applying` (аренда 120 с)
  отклоняет параллельный apply; просроченный может быть перехвачен следующей попыткой;
- branch apply перечитывает base ref: если base SHA отличается от показанного — `conflict`, записи нет;
- на первой попытке любая существующая branch с тем же именем — `conflict`, PPM её не двигает и не удаляет;
  повторная попытка того же действия сверяется с GitHub и признаёт своей branch, которая стоит на показанном SHA
  или ведёт от него (разработчик уже отправил коммиты), — это фиксируется как результат без новой записи;
- draft PR apply требует, чтобы head и base SHA совпадали с показанными (иначе `conflict`: в PR попали бы
  непросмотренные коммиты) и head отличался от base;
- своим PR считается только **открытый** PR с отметкой этого действия и ровно этими head/base; закрытый PR с
  отметкой — `conflict` «PR этой попытки уже закрыт» (исход `exists`), без повторного открытия и без дубликата;
  похожий PR без отметки не присваивается никогда (даже с тем же текстом). После успешного apply повтор команды
  возвращает сохранённый результат (provider object id и canonical URL) без обращения к GitHub;
- сверка с GitHub выполняется, только пока исход неизвестен (ответ на запрос записи потерян, попытка умерла с
  арендой); после явного отказа GitHub (429, 422, …) повтор ведёт себя как первая попытка и ничего не присваивает;
- если сверка не может доказать исход — ветка с нашим именем не ведёт от показанного SHA, открытый PR без отметки
  появился после первой попытки, ответ 422 «already exists» не подтверждён повторным чтением — шаг закрывается
  `conflict` с честным сообщением «Не удалось подтвердить, создан ли PR (создана ли ветка) — проверьте в GitHub» и
  ссылкой (PR ветки / ветка), аудит `write_outcome: unknown`. «Чужой PR» говорится только когда доказано: открытый PR
  без отметки создан раньше первой попытки (с запасом на расхождение часов);
- созданные branch и draft PR сохраняются как Git objects и связываются с Work Item по canonical provider URL —
  так они попадают в проекции Холста.

## Ошибки провайдера и отмена

- rate limit (429; 403 с исчерпанным лимитом, `Retry-After` или текстом о secondary rate limit), отозванный токен
  (401), удалённая/приостановленная установка,
  permission drift (403, 422 при выпуске токена), правила репозитория/защищённые ветки (422), неподдерживаемый
  draft PR сохраняются как видимая ошибка (`failed`) без скрытого повтора; повтор — только явной командой
  пользователя и не раньше `retry_after` от GitHub;
- расхождение с preview (сдвинулась база/голова, имя занято, PR уже есть) — `conflict`: нужен новый preview;
- 401 GitHub никогда не возвращается браузеру как 401 (это разлогинило бы пользователя PPM): API отвечает
  409/429/502 с кодом ошибки;
- если запрос записи ушёл, а ответа нет (таймаут, 5xx, обрыв), или попытка умерла, держа аренду, исход считается
  **неизвестным**: шаг остаётся `failed` с `outcome_unknown` (или `applying`), отмена запрещена, доступно только
  «Повторить» — повтор сверяется с GitHub и фиксирует найденную ветку/PR как результат;
- отмена возможна только когда записи точно не было (`proposed`, `approved`, `failed` с известным исходом); после
  `applied` PPM ничего не удаляет в GitHub — ветку или PR закрывают в GitHub;
- каждый шаг аудируется, включая отказы (`apply_refused`, `cancel_refused`): инициатор, provider identity, запрос
  (тип, refs, SHA) и исход. `provider_write_performed` — была ли запись в этом запросе (`null` — неизвестно);
  `write_outcome` — состояние шага: `not_performed` (доказано), `unknown` или `exists`. Вытесненная попытка,
  успевшая записать, пишет в аудит URL созданного объекта. Имена веток перепроверяются и при apply.

## Флаг и откат

`PPM_GIT_WRITE_ENABLED=0` (по умолчанию): preview, approve, отмена и аудит работают, apply отвечает понятным отказом
«Запись в GitHub выключена администратором PPM», а раздел «Код» показывает, как сделать шаг вручную (команды
`git switch -c <ветка> <base SHA>` / ссылка на сравнение веток в GitHub). Откат: выключить флаг и отозвать write
scopes; ранее созданные объекты GitHub и read sync сохраняются. Миграция `ppm_git 0007` обратима; старые открытые
одношаговые предложения закрываются с кодом `GIT_WRITE_FLOW_SUPERSEDED` (обратная миграция восстанавливает их
статус и прежнюю ошибку). Откат миграции удаляет у новых действий SHA, связь шага 2 с шагом 1 и поля apply: история
шага 2 теряется, а после повторного применения такие действия не применятся (пустой SHA даёт `conflict` —
fail-closed); созданные в GitHub объекты и их Git objects/связи с задачами остаются.

## Отклонённый вариант

Не создавать автоматический «пустой» commit ради мгновенного draft PR. Это дополнительная запись в repository,
которой нет в preview, она загрязняет историю и смешивает создание branch с изменением кода.

## Rollout

1. Обновить GitHub App permissions (`Contents: Read and write`, `Pull requests: Read and write`) и повторно
   принять их в установке; в PPM нажать «Проверить права».
2. Пройти живой E2E на тестовом репозитории: Work Item → branch preview/approve/apply → commit/push →
   PR preview/approve/apply → draft PR → повтор apply без дубликата.
3. Только после этого включить `PPM_GIT_WRITE_ENABLED=1` для выбранного стенда.
