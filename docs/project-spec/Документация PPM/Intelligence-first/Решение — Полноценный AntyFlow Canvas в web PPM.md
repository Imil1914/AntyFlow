# Решение — Полноценный AntyFlow Canvas в web PPM

## Контекст

Desktop-прототип AntyFlow уже проверил основную модель взаимодействия: бесконечный холст, несколько досок,
богатые типы нод, визуальные связи, документы, файлы и AI-инструменты. Текущий web Canvas PPM был создан как
минимальный демонстрационный срез и содержит только часть этого опыта. Он не является целевым интерфейсом.

Владелец продукта 2026-09-19 зафиксировал новое обязательное требование: перенести в PPM вид и функциональность
AntyFlow, сохранив web-архитектуру, командную работу и строгие права доступа.

## Решение

1. **Desktop AntyFlow становится эталоном Canvas UX и функциональной полноты.** Перенос проверяется по явной
   матрице возможностей, а не по общему визуальному сходству.
2. **Canvas реализуется нативно внутри web PPM.** Iframe, Electron renderer в браузере и параллельное отдельное
   приложение не считаются переносом.
3. **У каждого проекта ровно один Project Canvas.** Он создаётся автоматически и наследует scope проекта.
4. **Project Canvas содержит много общих досок.** Доски можно создавать, открывать вкладками, переключать,
   переименовывать, упорядочивать, дублировать и архивировать. У проекта всегда остаётся хотя бы одна активная доска.
5. **Доска — единица загрузки, сохранения, версионирования и realtime-room.** Открытие одной доски не загружает
   snapshots всех остальных досок проекта.
6. **Все активные участники проекта видят Canvas и его доски.** РП и участники редактируют содержимое; наблюдатель
   работает read-only. Управление жизненным циклом досок ограничивается отдельными capabilities.
7. **Глобальный администратор PPM имеет серверно проверяемый доступ ко всем проектам, Canvas и доскам.** Эта роль
   не выдаётся через приглашение, workspace role или project role и не может быть получена обычным пользователем.
8. **РП и участник не получают сквозной доступ.** Они видят только проекты, куда добавлены явно.
9. **Источники истины не дублируются.** Plane остаётся владельцем задач, Vault — файлов и Markdown, Git provider —
   кода. Ноды AntyFlow показывают и редактируют их через bindings/adapters.
10. **Собственные Kanban/backlog AntyFlow переносятся как визуальные `work_items_view` ноды**, работающие с Plane
    Work Items. Они не создают вторую таблицу задач. Canvas-native checklist остаётся обычным содержимым ноды.
11. **Electron-возможности получают web/server эквивалент.** Прямые `fs`, IPC, webview, локальные secrets,
    terminal и kernel не попадают в browser bundle.

## Целевая иерархия

```text
PPM
└── Проект
    └── Project Canvas (1)
        ├── Доска «Главная»
        ├── Доска «Исследование»
        ├── Доска «Архитектура»
        └── ...
```

Доски общие для команды. Личная настройка `последняя открытая доска` не меняет общий порядок и содержимое.

## Роли и возможности

| Возможность | Глобальный администратор | РП проекта | Участник | Наблюдатель |
|---|---:|---:|---:|---:|
| видеть все проекты и Canvas PPM | да | нет | нет | нет |
| открыть Canvas доступного проекта | да | да | да | да |
| редактировать ноды и связи | да | да | да | нет |
| создать/переименовать/дублировать доску | да | да | да | нет |
| упорядочить доски | да | да | да | нет |
| архивировать/восстановить доску | да | да | нет | нет |
| изменить Canvas policy | да | да, в своём проекте | нет | нет |
| просматривать версии и audit | да | да | свои/доступные | нет |

Удаление последней активной доски запрещено. Hard delete доски не входит в пользовательский интерфейс.

## Матрица переноса AntyFlow

### Переносится с тем же пользовательским поведением

- бесконечный tldraw-холст, камера, zoom/pan/fit, выделение и multi-select;
- панель и каталог нод, drag-and-drop, command palette и горячие клавиши;
- несколько досок и быстрые вкладки;
- заметки, документы, списки, таблицы, код, схемы, изображения, референсы и презентации;
- связи между нодами, группировка, рамки, поиск и навигация по объектам;
- Work Item/Kanban/backlog представления;
- контекст связанных нод для Project Brain;
- визуальный язык, плотность и основные состояния AntyFlow.

### Переносится через web/server adapter

| Desktop AntyFlow | Web PPM |
|---|---|
| локальные файлы и `fs` | Project Vault и проверенные upload/download API |
| IndexedDB/файловые snapshots | server versions + browser cache |
| локальный AI provider и ключи | server provider profile/secret store |
| ChatGPT/Gemini/GLM webview | единая AI-нода через разрешённые model adapters |
| terminal/OpenCode | project agent/job с sandbox и audit |
| локальный Jupyter kernel | управляемый notebook job/runtime после отдельного security gate |
| AnythingLLM/OpenScience sidecars | внешние connectors или PPM services |
| desktop orchestration | Project Agents с preview/approval/audit |
| локальная/папочная синхронизация | project-authorized persistence и realtime |

Отсутствие Electron API не является основанием удалить пользовательский сценарий: для него проектируется безопасный
web-эквивалент. До появления эквивалента UI не показывает ложную работающую кнопку.

## Совместная работа

- один сохранённый board snapshot виден всей команде проекта;
- optimistic concurrency остаётся базовым fallback;
- realtime и presence подключаются к room конкретной доски после server authorization;
- reconnect не создаёт отдельную личную копию доски;
- конфликт никогда не перезаписывает более новую серверную версию молча;
- глобальный администратор использует те же API и оставляет audit trail.

## Миграция текущего Canvas

Существующий единственный snapshot проекта переносится в доску `Главная` без изменения project/canvas UUID.
История версий сохраняется и связывается с этой доской. Повторный запуск миграции идемпотентен. Неизвестные ноды
сохраняются как opaque payload и не удаляются.

## Последствия

- Canvas становится отдельным крупным потоком работ `AF`, а не побочным пунктом I0.4;
- текущий minimal Canvas сохраняется как миграционный фундамент, но не как целевой UX;
- потребуется versioned schema нод и досок, серверные adapters и отдельный parity gate;
- полный перенос выполняется поэтапно под feature flags, без остановки Work Items/Vault;
- старый запрет на самостоятельные Kanban/backlog заменяется запретом на вторую базу задач: визуальный интерфейс
  разрешён только поверх Plane Work Items.

## Отклонённые варианты

1. **Оставить минимальный Canvas.** Не соответствует продуктовой ценности и уже реализованному AntyFlow.
2. **Встроить Electron renderer/iframe.** Ломает web security, права, совместную работу и поддержку.
3. **Хранить отдельные Canvas каждого участника.** Противоречит командной работе и создаёт расходящиеся источники.
4. **Один огромный snapshot на все доски.** Ухудшает загрузку, конфликты, realtime и восстановление.
5. **Скопировать desktop Kanban как отдельные задачи.** Создаёт вторую базу задач рядом с Plane.

## Rollback

Каждый этап включается отдельным feature flag. При rollback новый UI выключается, но board rows, versions и
snapshots не удаляются. Текущая доска `Главная` остаётся доступна через совместимый минимальный renderer.
